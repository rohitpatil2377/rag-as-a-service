# RAG as a Service — Backup & Disaster Recovery

This is the operational runbook for backing up and recovering an RAG as a Service deployment. It
covers **what to back up, why, how, and how to restore**, plus the recovery-objective guidance a
regulated buyer (or your own ops team) expects.

> Scripts: `scripts/backup.sh`, `scripts/restore.sh` (also `make backup`, `make restore`).

---

## 1. The data model — authoritative vs derived

RAG as a Service spreads state across five stores. The single most important fact for DR is that **not
all of them are authoritative** — two hold the source of truth, and the other three are *derived*
and can be **rebuilt** from it:

| Store | Holds | Class | If lost… |
|---|---|---|---|
| **PostgreSQL** | Document catalog + metadata, the **tamper-evident audit chain**, and every global registry (accounts, API keys, KB list + Trash, model connections, schedules, feature flags, egress approvals, ingest jobs) | **AUTHORITATIVE** | Not recoverable except from backup |
| **MinIO** (object store) | The **raw original document bytes** | **AUTHORITATIVE** | Not recoverable except from backup |
| **Qdrant** | Embedding **vectors** per KB | Derived | Rebuild by re-embedding the raw bytes |
| **OpenSearch** | **BM25** keyword index per KB | Derived | Rebuild by re-indexing the raw bytes |
| **Redis** *(optional)* | Rate-limit / cache / leader-lock coordination | Ephemeral | Nothing to back up |

**Implication:** a *minimum viable backup* is **PostgreSQL + MinIO**. From those two, every KB's
search index (Qdrant + OpenSearch) can be regenerated by re-indexing (`reindex_document` reads the
raw bytes and rebuilds the chunks/vectors/BM25). Backing up Qdrant/OpenSearch too simply makes
**recovery faster** (no re-embedding), at the cost of larger backups.

## 2. What the backup captures

`scripts/backup.sh` writes a timestamped directory:

```
backups/20260713-XXXXXX/
  postgres.dump        # pg_dump -Fc — consistent logical dump (AUTHORITATIVE)
  minio/               # raw document bytes                     (AUTHORITATIVE)
  qdrant/              # vector collections   (derived, for fast RTO)
  opensearch/          # BM25 indexes         (derived, for fast RTO)
  MANIFEST.txt
```

- **PostgreSQL** uses `pg_dump -Fc` — a **transactionally consistent**, version-portable dump.
- **MinIO / Qdrant / OpenSearch** are copied from their data volumes.
- Set `RAG_BACKUP_DERIVED=0` to back up **only the authoritative stores** (much smaller) and rely
  on re-index for the derived ones on restore.

### Consistency note
`pg_dump` is transactionally consistent on its own. The object/vector volume copies are taken from
a **running** store; for object stores this is safe (objects are immutable once written), and any
document mid-ingest at backup time is simply re-ingestable. For a **strict** point-in-time backup
in production, quiesce writes briefly (pause the ingest worker / scale the API to read-only) or use
the stores' native snapshot APIs (Qdrant snapshots, an OpenSearch snapshot repository, MinIO
bucket replication) — the same script structure applies.

---

## 3. Running a backup

```bash
make backup                      # → backups/<timestamp>/
# or
scripts/backup.sh /mnt/backups/ragaas-nightly
RAG_BACKUP_DERIVED=0 make backup   # authoritative only (smaller; rebuild indexes on restore)
```

Ship the resulting directory off-box (object storage in a **second sovereign region**, or tape) —
a backup on the same host does not survive host loss. Encrypt at rest in transit to the DR site;
the raw bytes are already PII-masked in the *indexed* copy, but the **original** bytes in MinIO are
sensitive, so treat the backup as confidential.

**Schedule** it with cron / a systemd timer (e.g. nightly full, plus a WAL-archiving setup on
PostgreSQL for point-in-time recovery if your RPO must be < 24h).

---

## 4. Restoring

```bash
scripts/restore.sh backups/20260713-XXXXXX     # or: make restore BACKUP=backups/20260713-XXXXXX
```

The restore:
1. `pg_restore --clean` rebuilds the PostgreSQL state (catalog + audit + registries).
2. Stops each store, swaps in the backed-up MinIO / Qdrant / OpenSearch data, restarts it.

If the backup **omitted the derived stores** (`RAG_BACKUP_DERIVED=0`), the search indexes come
back empty — **rebuild them** by re-indexing each KB's documents (the raw bytes + catalog are
present, so re-index regenerates chunks + vectors + BM25):

```bash
# rebuild a KB's search index from its authoritative raw bytes
for doc in $(curl -s "$API/v1/kb/$KB/documents" -H "authorization: Bearer $TOKEN" \
             | python3 -c "import sys,json;[print(d['doc_id']) for d in json.load(sys.stdin)]"); do
  curl -s -X POST "$API/v1/kb/$KB/documents/$doc/reindex" -H "authorization: Bearer $TOKEN"
done
```

### Verifying a restore (non-disruptive)
You can prove a `postgres.dump` is valid without touching the live system by restoring it into a
throwaway database and counting rows:

```bash
docker exec ragaas-dev-postgres-1 psql -U rag -c 'CREATE DATABASE verify'
docker exec -i ragaas-dev-postgres-1 pg_restore -U rag -d verify < backups/.../postgres.dump
docker exec ragaas-dev-postgres-1 psql -U rag -d verify -c \
  "SELECT schemaname, count(*) FROM pg_tables WHERE tablename='documents' GROUP BY 1;"
docker exec ragaas-dev-postgres-1 psql -U rag -c 'DROP DATABASE verify'
```

**Test your restores regularly** — an untested backup is not a backup. The audit chain is
self-verifying: after a restore, the compliance attestation walks the SHA-256 chain and confirms
integrity, so a corrupted restore is detectable.

## 5. Recovery objectives (RPO / RTO)

| Backup strategy | RPO (data-loss window) | RTO (time to recover) |
|---|---|---|
| Nightly full (authoritative + derived) | up to 24h | minutes (restore volumes) |
| Nightly full (authoritative only) | up to 24h | minutes + **re-index time** (re-embedding is the cost) |
| Nightly + PostgreSQL WAL archiving | seconds–minutes (PITR) | minutes–hours |
| Continuous (MinIO replication + streaming WAL) | near-zero | minutes |

**Recommendation for a production sovereign deployment:** nightly full backups (authoritative +
derived) shipped to a second sovereign region, **plus** PostgreSQL WAL archiving for a tight RPO on
the authoritative metadata/audit. Multi-replica HA (Redis) covers *availability*; backups cover
*durability* — you need both.

---

## 6. What is NOT yet automated (roadmap)

- **In-product scheduled backups** with a console button + status (today: cron the script).
- **Native snapshot APIs** wired in (Qdrant snapshot / OpenSearch snapshot repo / MinIO replication)
  for strict point-in-time consistency without quiescing.
- **`reindex-all` endpoint** so DR-lite rebuild is one call instead of a loop (today: per-document
  re-index).
- **Cross-region replication** as a managed feature.

These are additive; the scripts here are the operational baseline and are safe to run today.


## Key custody (KMS) — the other half of DR

Restoring the stores brings back *ciphertext*; it is worthless without the keys. Tenant data
is envelope-encrypted (`rag_common.crypto`): each tenant has a Data Encryption Key (DEK)
wrapped by a Key Encryption Key (KEK). Where the KEK lives is the custody decision:

- **`RAG_KMS_BACKEND=local`** (default) — the KEK is derived from the platform master key.
  Back up the master key separately and as carefully as the database; losing it is
  unrecoverable data loss, and a backup that includes it is as sensitive as the data.
- **`RAG_KMS_BACKEND=external`** — the KEK never leaves a sovereign **KMS/HSM**
  (`rag_common.kms.ExternalKmsKeyWrapper`, wired for Vault Transit; `RAG_KMS_ENDPOINT` +
  `RAG_KMS_KEY_ID`, egress-allowlisted). DR then has two independent custodians — the store
  backups AND the KMS — and **crypto-shred is real**: revoke the KMS key and every wrapped DEK
  (in every backup, past and present) is permanently un-unwrappable. Back up / replicate the
  KMS per its own DR runbook; a store restore is only usable while the KEK still exists.

DR drill checklist: (1) restore stores (`make restore BACKUP=…`), (2) confirm the KMS/KEK is
reachable, (3) verify the grant table (restore.sh does this), (4) verify audit-chain integrity
via `GET /v1/kb/{id}/attestation`.
